# Plan: the run file, asked before the plan

## Result

Today the user is asked how a run ends only at its end, and e2e's access comes from `AGENTS.md` or the build's opening message. After this plan, the new `runweld run-file` skill writes `.runweld/workflow/plans/<slug>.run.toml` before the plan. It starts from the project's last run file and asks only what differs. The CLI checks the file and `approve` requires it. `build start` gives the run a port and a data directory of its own. Plan, the implementer's brief and e2e read the file.

## Approach

The CLI gains `run new|check|show <plan>`. The plan's path need not exist yet. Phase 1 builds the contract and `approve`, phase 2 the allocation and the brief, and phase 3 the prose that uses them.

- The contract, which is the interface between the phases. Each key of a fixed section is required, except `dev` and `url`:
  - `[finish]`: `how` (`merge-request`, `ff-only` or `no-ff`), `target` (a branch) and `delete_backups` (a boolean).
  - `[checks]`: `phase` and `full`, each a list of commands, where empty means none, plus `dev` and `url`.
  - `[isolation]`: `worktree`, `port` and `data_dir`, each a boolean.
  - `[run]`: any key with a string, number or boolean value.
  - `{port}` and `{data_dir}` in a `[checks]` value stand for the run's allocation.
  - `run check` refuses an unknown section or key, a missing key, a wrong type, a value outside its list and a placeholder whose allocation is off. It prints all problems at once, in the epic's `<code>: … — fix:` form. Code refuses only what the next step cannot use.
- The run file names the plan: `YYYY-MM-DD-<branch>.run.toml`, with each `/` in the branch written as `-`, and the plan file takes the same name with `.md`. One name is chosen once, and `feat/x` never collides with `fix/x`.
- `run new` copies the newest run file in `.runweld/workflow/plans/` by modification time, else the example the skill ships. It refuses to overwrite a file. Finding the last run is mechanical.
- The skill shows the copied values in one message. It asks what differs, and what this task needs that no key covers. A first run fills `[checks]` from the `AGENTS.md` Environment block and leaves `AGENTS.md` alone. That keeps the decided order: grill → prototype → run file → plan.
- For each new secret the skill asks whether to write it directly or as a pointer, `keychain:<service>/<account>`. Code never resolves a pointer, so a secret given that way stays out of the state and the briefs.
- `approve` refuses a draft without a valid run file and records the file's values. A plan it adopts goes on without one. After approval the file changes by an edit and `approve` again. Until then every reader uses the recorded values and reports the drift, as plan 1 does for plan text, so a run cannot widen what it may do unseen.
- `build start` allocates what `[isolation]` asks for:
  - a port from a range in code, free on the machine and not held by any plan `status` lists;
  - the directory `.runweld/workflow/plans/<slug>.data/`.
  It records both, prints them among its facts, and `status` shows them. With `worktree = true` and no `--worktree`, it refuses unless given `--note`, so the orchestrator still names the path.
- `run show` prints the values with the allocation filled in, and `--json` gives them to code. Through it, plan 3 reads `[checks].full` and plan 4 reads `[finish]`. Plan writes Checks from `[checks]`. Verify sets up only what `run show` gives and reports everything else as `not reached: needs <what>`. Verify used alone, without a plan, keeps the Environment block.
- The implementer's brief adds:
  - `[checks].phase`;
  - every `[run]` key as written, since which agent needs which key is a judgment;
  - every `## Spec` entry with its ID, statement and `Done:` items. A phase names no Done items, so which entries apply is the implementer's call.
  Territory prints once, in the phase's own text.
- A draft's Status line writes `base` as `—`, and `build start` writes the SHA.
- `sync_epic` checks that the epic exists before it takes the lock. A missing epic is reported as a fact, and the state change goes on.

## Out of scope

- `finish` reading `[finish]` and code running `[checks].full`: plans 4 and 3.
- Briefs for the e2e worker and the reviewer: plan 3. Removing a run's data directory after the merge: plan 4.
- `AGENTS.md`, its Environment block, and `docs/pipeline.html`.

## Done and Spec

```text
## Done

1. Run `scripts/check` and `scripts/test` → both exit 0.
2. In a throwaway repo with no run file, run `run new <plan>` → the run file is a copy of the shipped example with an empty `[run]`, and the output names it; `run check` on it is silent. Add a newer run file, then run `run new` for another plan → it copies the newer one; run it again → refused, the file unchanged.
3. Give a run file `mode = "x"` and `how = "squash"` under `[finish]`, no `full` under `[checks]`, a `[deploy]` section, a table and a list under `[run]`, and `dev` using `{port}` with `port = false` → `run check` exits 1 with one line per problem, naming its section and key. `admin_pwd = "keychain:app/admin"`, `can_remove_tasks = false` and `quota = 20` under `[run]` pass.
4. `approve` a draft with no run file → exit 1, a fix naming `runweld run-file`, no JSON; with a bad one → exit 1 with `run check`'s lines; with a good one → approved. Change `delete_backups` in the file, or `quota = 1` to `quota = true` → `status` and `run show` report the drift and show the approved value; `approve` again → the new value, and `status` lists the changed keys in the plan's history. A plan at `building` with no run file → adopted.
5. Two plans in one repo both have `port = true` and `data_dir = true`. Run `build start` on each while something listens on the first port of the range → two different ports, neither of them the busy one, and two directories that exist, all among the printed facts; `run show` prints `dev` with them filled in. With `worktree = true`, `build start` without `--worktree` → refused; with `--note` → built here, the note in `status`.
6. Run `brief implementer 2` on a plan with three `## Spec` entries → the file holds `[checks].phase`, every `[run]` key as written with the keychain pointer unresolved, each entry's ID, statement and Done items, and one `Territory:` line.
7. Delete the epic's directory after `approve`, then run `phase start 1` → the phase starts, a line says the epic is missing, and there is no traceback.
8. In a throwaway repo with an earlier run file, end a grill, decline the prototype and go on → `runweld run-file` shows the copied values in one message and asks only what differs and what the task needs. The plan takes the run file's name, Checks takes `[checks]`, and a Done case the run file gives no access for is `you check` — you check
9. Run `runweld verify` on a plan whose use case needs a login its run file lacks → that case is `not reached: needs <the login>`, and the dev server it starts uses the run's port — you check

## Spec

+ run — The run file
  About: `.runweld/workflow/plans/<slug>.run.toml`, written before the plan: what a run may do, its checks, its isolation and how it ends.
+ run#starts-from-last — A new run file starts as a copy of the project's latest one, or of the shipped example with an empty `[run]` when there is none
  Why: the user is asked only what differs from the last run, and no sample login reaches a run
  Done: 2
+ run#contract-checked — A run file's fixed sections refuse an unknown or missing key and a value outside its type or list; its `[run]` section takes any key with a plain value
  Why: no agent invents a field, and code hands on what it cannot judge
  Done: 3
+ run#required-to-approve — A draft is approved only with a run file that passes its check
  Why: what a run may do and how it ends is asked before the plan, not mid-run
  Done: 4
+ run#changes-through-approve — After approval every reader uses the run file's approved values and reports a changed file until `approve` runs again, which records the changed keys in the plan's history
  Why: a run cannot widen what it may do without it showing
  Done: 4
+ run#isolated — Plans of one project being built get a port and an app data directory of their own from code
  Why: runs of one project go side by side
  Done: 5
+ run#secrets-as-written — Code hands `[run]` values on as written and never resolves a keychain pointer
  Why: a secret given by pointer stays out of the state and the briefs
  Done: 6
+ run#e2e-within — e2e sets up only what the run file covers; what it does not cover is `not reached`
  Why: nothing pulls the user in mid-run
  Done: 9
+ build#brief-carries-spec — An implementer's brief lists every `## Spec` entry of the plan with its ID and Done items
  Why: tests carry the rule's ID, which lives only in the plan until `spec write`; a run lost a judge round to it
  Done: 6
~ build#recover-plan-state — A plan without state is adopted by `approve` as its file stands; no other command but `spec` and `run` runs on it
  Why: a plan mid-build keeps its recorded progress; the run file is written and checked before the plan has state
```
